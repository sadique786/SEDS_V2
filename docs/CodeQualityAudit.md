# Code Quality Audit

This audit records source-observed risks and recommended follow-up. It does not implement fixes. Severity indicates practical impact: **High** can prevent core use or safe deployment; **Medium** limits correctness/reproducibility; **Low** is maintainability or cleanup work.

| Issue | Severity | Impact | Recommended resolution | Blocks fresh install? | Blocks deployment? |
|---|---|---|---|---|---|
| Database schema mismatch | High | `create_tables()` creates five columns, while `insert_detection()` requires `event_id`; fresh-database persistence fails. | Design a versioned migration after inspecting existing databases; preserve rows and test fresh and upgraded schemas. | No, package installation can complete. | Yes, reliable detection persistence is blocked. |
| DetectionService integration | High | Service persists and logs only; it does not run the rules engine or evidence manager. There is no complete detector-to-service orchestrator. | Introduce an explicit orchestration boundary that applies configured rules, records outcomes, and integrates evidence with error handling. | No. | Yes, complete automated detection workflow is absent. |
| EventManager scope | Medium | Generates an `EVT-` identifier only; no temporal/spatial aggregation or event lifecycle exists despite historical naming. | Specify event identity and aggregation requirements, then implement with focused tests. | No. | Blocks any deployment requirement for grouped events, but not component initialization. |
| CameraManager behavior | High for live-camera scope; Low for still-image use | `load_image()` calls `cv2.imread()` and returns `None` on unreadable input without validation. It does not open CSI/USB cameras. | Validate image reads and design camera acquisition separately with hardware tests. | No. | Yes for live-camera deployment; still-image inference remains a separate path. |
| Empty-database dashboard edge case | Medium | SQLite `AVG` returns `None`; Home calls `round(None, 2)` and can fail when there are no detections. | Add an explicit empty-state UI and test zero-row and populated database behavior. | No. | Can block first dashboard use on a new empty database. |
| History column mismatch | High | History assigns six labels, while a fresh schema returns five columns; populated history rendering may fail. | Align selected columns and labels after defining/migrating the schema; add dashboard query tests. | No. | Yes for usable detection history on a fresh DB. |
| Relative paths and configuration | Medium | Config, database, logs, and model use working-directory-relative paths. Running from another directory can resolve the wrong/missing files. `ConfigManager.get()` raises on missing keys; some YAML flags are unused. | Resolve paths from a known project/config root, validate configuration, document defaults, and distinguish active settings from placeholders. | No when launched from repo root; may block launch from another directory. | Yes for reliable service startup until paths/settings are controlled. |
| No automated tests | High for change confidence; Medium for prototype | Test files execute scripts at module scope and mostly print values without assertions; some mutate DB, logs, or tracked captures. No pytest suite exists. | Refactor to isolated pytest tests with assertions, fixtures, explicit markers, and no import-time side effects. | No. | Blocks confidence in release readiness, not initial package installation. |
| Dependency management | Medium | `requirements.txt` is a flat list of pinned direct and transitive packages. `python-dotenv` appears unused; large PyTorch/Ultralytics dependencies and exact pins may not be portable across platforms. | Declare a small direct set plus an explicit lock/constraints strategy; verify supported Python and platform combinations before pruning pins. | Potentially: unsupported wheel/version combinations can break installation on a platform. | Yes until Raspberry Pi package compatibility is established. |
| Model distribution and provenance | Medium | Detector requires `models/yolov8n.pt`; model weights are not reliably present in a fresh clone and no checksum manifest is tracked. | Document the pinned Ultralytics acquisition path and record model version plus SHA-256; keep large weights outside Git. | No for non-model setup; yes for YOLO inference if weight acquisition fails. | Yes for reproducible inference until acquisition/provenance is controlled. |
| Hardware/performance validation gap | High for target deployment | No Raspberry Pi 4B camera, inference, memory, thermal, throughput, uptime, or recovery results are available. | Run a recorded hardware validation plan with model checksum and representative inputs before deployment claims. | No. | Yes; deployment and performance remain unvalidated. |
| Error and resource handling | Medium | SQLite connections are manually closed only after successful operations; OpenCV input failure is not checked; broad application-level recovery is absent. | Use reliable connection cleanup, validate inputs, and return/log actionable errors; cover failure paths in tests. | No. | Risks long-running reliability and diagnosability. |

## Additional observations

- The config includes tracking, alert, cooldown, image-save, and video-save options without corresponding complete integrations. Treat them as placeholders.
- Evidence metadata writing exists, but the service does not automatically store image files or call the metadata writer.
- Existing tests can overwrite `captures/visualized_elephant.jpg` or write to shared database/capture paths; isolation is needed before routine test execution.
- The Streamlit dashboard is basic and has no explicit database error/empty-state handling.
- No CI workflow, formal package metadata, or validated Raspberry Pi deployment process was found during this audit.

## Scope and next actions

These findings are documentation-only. The recommended order is to plan the database migration, establish isolated automated tests, then implement the pipeline and evidence integration with reviewable behavior. Dependency cleanup and Raspberry Pi work should follow reproducible tests and platform measurements. Do not infer that any recommendation has been implemented by this report.
